# Final evaluation report: release candidate RC1 (pipeline v5) on a staged subset of the frozen test split

> **Correction note, 2026-11-25 (no result changed).** The correct replicate coverage of the whole RC1 evaluation in `results/final` is: replicate 0 on all **35** sites, replicate 1 on **12** sites, replicate 2 on **8** sites (23 sites have replicate 0 only). Earlier wording such as "12 sites with replicates 0 to 2" describes stage 1 only and over-states replicate 2 (8 of the 12 sites). This is a reduced evaluation, not the A3-protocol deliverable (L0 vs G0 on at least 50 cases); no claim that G1 or the graph arm is superior is established.

Date 24 Nov 2026. Provider and model: AxForge `glm-5.3-flash` (key slot 1) for every condition; temperature 0; live requests only (no cache); shared 30 s start-to-start pacing. This is a **staged, reduced evaluation, not the full original protocol** (section 2). All figures below come from `results/final/` and are regenerated by the commands in section 9.

## 1. What was evaluated
- **Implementation:** RC1, code fingerprint `ee3d8d873a6e939451650d031a919799138e621859f79bdd91994af3f6456b51` (28 behaviour files, recorded in every run's metadata; all 128 records share it). Pipeline v5: symptom from the visible tests run on the base commit, labelled evidence, deterministic diagnostics findings, symptom-aware lexical retrieval (both arms) and symptom-derived graph anchors (G only), validated diagnosis (claim checks, no budget loss on rejected calls), target validation, scoped patches, visible-test feedback with provenance, hash-bound approval.
- **Conditions (formal 2x2 preserved):** L0, G0, L1, G1 = retrieval arm (L lexical, G graph) x feedback (0 none, 1 visible-test feedback on attempts 2 and 3). Up to 3 attempts per case; the hidden suite runs once on the frozen final patch and is never shown to a model.
- **Dataset:** the frozen test split (`datasets/manifests/test.json`, hash verified against `test.sha256` before use), not modified. Cases were drawn blind with a recorded seed (`results/final/selection-rc1.json`, written before any model call): one case per variant group from 12 of the 35 groups (6 of 20 code groups, 4 of 9 configuration groups, 1 of 3 insufficient-evidence groups, 1 of 3 runtime-dependency groups). A replicate-2 subset of 8 of those 12 cases was drawn with a second seed before that replicate (`selection-rep2.json`).
- **Shared diagnosis:** because feedback acts only inside the patch loop, L1 and G1 were run as patch-stage runs starting from the saved, hash-verified diagnosis of the L0 and G0 run of the same case and replicate. L1 therefore differs from L0 only in feedback, and G1 from G0 only in feedback. Diagnosis metrics exist for L0 and G0 only.

## 2. Deviations from the original protocol (explicit)
| Original protocol | What was done | Why |
|---|---|---|
| 151 test cases | 12 cases (12 of 35 variant groups) | the formal design needs about 36M tokens; the AxForge allowance (3M, 1.26M already used before this evaluation) allowed about 1.6M |
| 3 independent replicates of everything | replicates 0 and 1 on 12 cases, replicate 2 on 8 of them (36 planned case-runs per condition for 12 cases; 32 executed) | the allowance left after replicate 1 could not fund a full third replicate; replicate 2 was reduced by a pre-declared seeded draw, not by results |
| four independent runs per case | diagnosis shared between L0/L1 and between G0/G1 | feedback cannot change a diagnosis; this isolates the feedback factor and saves about 25% of the tokens |
| one pipeline | v5 RC1 is the pipeline for this evaluation; v4/v3 are historical | owner approval (24 Nov 2026) |
The independent fault-site unit is the variant group: 12 sites, one case each (stage 1; stage 2 later added 23 sites at replicate 0, see the correction note above). The replicate requirement (3 replicates of all cases) is **not met**; 2 of 3 replicates are complete for all 12 cases and a third exists for 8. No claim is made that the original protocol was completed.

## 3. Execution record
- 12 runner invocations (4 stages x 3 replicates), 239 live model requests, 128 case-runs recorded (L0 32, G0 32, L1 32, G1 32), **0 provider failures, 0 `provider_error` artifacts, 0 failed requests in the ledger**, no retries, no provider switch. The AxForge ledger rose from 1,255,286 to 2,847,336 committed tokens: **1,592,050 tokens** for the evaluation (L0 695,466; G0 702,196; L1 95,698; G1 98,690), 152,664 left of the key's 3,000,000 allowance.
- Hidden tests ran once per final patch (counts only recorded), never as feedback. The leak guard (hidden-only names, files and paths blocked everywhere; shared test names allowed only in verified spans) checked every request; no run was blocked. Every run's inputs (diagnosis, evidence) for the patch stages were verified against frozen hash manifests (`frozen-rep0/1/2.json`).

## 5. Graph versus lexical retrieval (paired, same case and replicate)
Paired outcomes (32 pairs): diagnosis exact-function/key both correct 25, G only 1, L only 0, neither 6; fixed both 25, G only 1, L only 0, neither 6 (the 6 are the abstention and runtime cases, which have no repair). Tokens: G used fewer tokens than L in 21 of 32 pairs and more in 11 (mean difference +210 tokens, i.e. no meaningful difference). The only repair-outcome difference is the configuration case `coupons_valid_until` in replicate 0 (L0 ended with a rejected final submission, G0 fixed it); in replicates 1 and 2 both arms fixed it. Diagnosis class differs in 4 pairs (G only correct 3, L only correct 1): the differing pairs are this same case and the runtime-dependency case `lab_db:catalogue`, where the failure flips between the arms from one replicate to the next (L0 correct in r1 only, G0 correct in r0 and r2), i.e. it behaves like sampling noise, not an arm effect. **The evidence does not support a claim that graph retrieval improves or degrades diagnosis or repair on this sample:** code and configuration cases were solved by both arms, retrieval records (`retrieval.json`, `context_sent.json` per case) show both arms retrieved the relevant chunks, and one difference of one case-run is within the replicate-to-replicate disagreement (L0: 1 of 12 cases changed outcome across replicates; G0: 0).

## 6. Feedback (F0 versus F1)
**No feedback opportunity arose.** In all 96 patch case-runs of L0 and G0 the first attempt was verified (attempts = 1 whenever a patch was made), so L1 and G1 reproduced L0 and G0 exactly. By the pre-declared criterion (an F0 first-attempt failure followed by an F1 pass at attempt 2 or later that actually received feedback), the number of feedback benefits is **0** and of feedback harms is **0**; the feedback machinery (visible-only provenance, per-test assertion text, previous-edit summary, guard v2) was exercised only by unit tests and by the earlier development runs, not by this evaluation. Nothing in these results shows that feedback helps or hurts. (A development case outside this evaluation, `low_stock_level`, showed three identical failed first-style attempts without feedback and is the kind of case that would test F1.)

## 7. Provider reliability, tokens and latency
- Provider failures: none (0 of 239 live requests). Mean case-run latency (model plus sandbox) about 101 s (L0) and 108 s (G0) and about 19 to 21 s for the patch-only L1/G1; mean model time per diagnosis run 88 s (L0) and 96 s (G0).
- Tokens: about 22k per diagnosis+patch case-run in L0/G0 and about 3.0k for a patch-only L1/G1 run. The planning estimate (about 750k per 18 cases) was close: replicate costs were 570,146 (12 cases), 623,656 (12 cases) and about 398k (8 cases).

## 8. Comparison with historical v4/v3 results (not pooled, not comparable)
Earlier official-tier pilots and screening runs (patch_v3 `pilot8`, patch_v4 screening) used different prompts and pipelines, a different diagnosis input (no symptom), no deterministic findings, cached replays in some runs, different case sets and one replicate. In those runs the 8 pilot cases gave 1 verified patch (v3) and the 11 screening cases gave 0 verified patches (v4); diagnosis was dominated by abstentions and one recurring wrong diagnosis. Only `shop_api-008` appears in both sets: abstained under v3, and fixed in 3/3 replicates under RC1 in both arms. Because the case sets, pipeline, prompts and diagnosis inputs all differ, the historical numbers are **not** compatible with RC1 numbers and no pooled or difference statistic is given; the contrast is qualitative evidence about what the symptom and validation changes did on cases of these kinds, not a controlled v4 versus v5 comparison (no paired v4 run on the RC1 cases exists).

## 9. Reproducibility
- Selection and freeze files: `results/final/selection-rc1.json`, `selection-rep2.json`, `rc1-fingerprint.txt`, `frozen-rep{0,1,2}.json`, the test manifest hash in `datasets/manifests/test.sha256`.
- Run: `bash scripts/final_eval.sh K [CASES_FILE]` (K = replicate index; verifies the fingerprint, runs L0, G0, freezes their outputs, then L1 and G1 from the shared diagnoses; halts at the first failure; never retries).
- Report: `python -m traceforge.evaluation.final_report --manifest ../datasets/manifests/test.json --final-dir ../results/final --out-dir ../results/final/report --replicates 0,1,2 --selection ../results/final/selection-rc1.json` (from `backend/`): tables (`report/tables/*.csv`), `results.json`, `results.md` and five SVG figures in `report/figures/`.
- Artifacts per case run: prompt hashes (`requests.jsonl`), evidence, symptom, retrieval, context sent, diagnosis, repair attempts with test outcomes, hidden counts, run metadata with the fingerprint.

## 10. Limitations
- 12 of 151 cases (12 sites), 2 full replicates plus a reduced third: the results describe these sites, not the split; no significance or generalization claim is made.
- The symptom exposes the faulty function's name through visible test names and endpoints in code cases (measured earlier on the dev split); high code-fault accuracy partly reflects that, not independent source reasoning.
- All first attempts succeeded, so feedback, the iterative loop and the scope policy's rejections were not exercised by this evaluation.
- The single runtime-dependency case showed a model-output failure mode (no tool call) in 3 of 6 diagnosis runs; the diagnostics for runtime outages were not exercised beyond that case.
- One model (a reasoning model, nondeterministic at temperature 0), one provider key, one evaluation window.
- The scorer's file metric is meaningful only for code targets (config targets are keys); hidden-suite regressions are visible as counts only; selection-based sampling (one case per group) does not weigh groups by size.
- Some selected cases appeared earlier in historical official-tier runs (e.g. `shop_api-008` in the v3 pilot) and several test cases were read offline during analysis (no tuning on them); the blind seeded draw does not remove that history.
